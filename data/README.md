# Transit source data

## `bus-routes-2026-27.json` — official timetable (authoritative)

Transcribed from `2026-27 Bus Routes.pdf` (5 pages): 44 morning routes —
Vijayawada `VV-1`…`VV-21`, Guntur `GV-1`…`GV-20`, Tenali `TV-1`…`TV-3`. Every route ends at
VIT-AP Campus at 8:45 AM. The PDF has no evening/return timetable, bus numbers, drivers, seat
capacity or coordinates, so none of those are imported.

- Pickup-point names and times are kept **exactly as printed** (including spellings such as
  "Pertol", "TadepaIii", "Commisioner"). Only repeated spaces are collapsed when displayed.
- Points are **not merged across routes by name**: "Market", "Bus Stand", "Varadhi", "Chillies"
  etc. appear on several routes and may be different places. Each point gets a stable ID
  `stop-<route>-<seq>` (e.g. `stop-vv-1-08`); the campus is the single shared `stop-vit-ap-campus`.
- `reviewNotes` lists the ambiguities that need confirmation from the transport office
  (e.g. the GV-3 time that goes backwards, the split VV-9 first row).

`src/lib/official-schedules.ts` builds stops, routes and unassigned trips from this file; the
build is deterministic, so re-importing is idempotent. `tests/timetable.test.ts` checks route
coverage, ordering, times, idempotency and that no coordinates or assignments are invented.

## `stop-geocodes.json` — candidate coordinates (NOT verified)

Generated by `node scripts/geocode-stops.mjs` using OpenStreetMap Nominatim (1 request/second,
cached; re-run with `--retry-unresolved` to retry misses). Matches farther than 50 km from campus
are rejected. Each entry is either:

- `geocoded_unverified` — a Nominatim match; shown on the map as **approximate**. Must be
  reviewed (ideally replaced by a surveyed bus-bay point) before being relied on.
- `unresolved` — no acceptable match; the stop has no coordinate (NaN) and is listed but not
  drawn on the map.

To record a verified position, edit the entry: set `latitude`/`longitude`, set
`"status": "surveyed"` and add a `"source"` describing who verified it and how. The script never
overwrites existing entries.

Geocoding data © OpenStreetMap contributors, ODbL.

## `route-geometries.json` — planned road paths

Generated by `node scripts/build-route-geometry.mjs` (re-run after changing geocodes; only routes
whose inputs changed are re-requested; `--refresh` forces all). It calls OSRM once per route with
the route's located stops in timetable order and stores the simplified road path (~3 m tolerance).
The app reads this file and never calls a router at request time.

Before routing, a stop's geocode is **rejected** when it contradicts the timetable — e.g. the
printed minutes to its neighbours can't cover the distance, or it forces a large detour. Generic
names ("Bus Stand", "Market") often match a same-named place elsewhere; this check catches them.

Per route: `status` is `ok` (road path through every stop), `partial` (some stops have no location
or were rejected, or a leg looks suspect — see `excludedStops`/`problems`) or `unavailable` (fewer
than two located stops; nothing is drawn). The map never falls back to straight lines.

Caveats: OSRM's `driving` profile is a car profile and doesn't know bus restrictions; the public
demo server (`OSRM_BASE_URL` default) is for light use only. A partial path skips unlocated stops,
so it may not pass through them. Have the transport office confirm paths before relying on them.

Route geometry © OpenStreetMap contributors (ODbL), computed with OSRM.

## Live GPS

Devices `POST /api/trips/{tripId}/location` with `Authorization: Bearer <device key>` and JSON
`{ latitude, longitude, accuracyMeters, speedKmH?, heading?, recordedAt? }`. Keys are configured
per bus in `GPS_DEVICE_KEYS` (`busId:key,…`, keys ≥ 24 chars). A report is accepted only when that
bus is assigned to the trip; reports older than the latest stored one are ignored, invalid values
get 422, and more than one report per second gets 429. The driver page (`/driver`) can act as the
device using the phone's geolocation.

Each observation is matched to **that trip's** planned road path (not to arbitrary roads): within a
tolerance of 2× the reported accuracy (30–75 m), consistent with direction of travel and previous
progress. The raw observation is always stored; the matched point is stored separately and shown
only when the match succeeds. Otherwise the map shows the raw point with its accuracy circle and
the reason (`off_route`, `low_accuracy`, `ambiguous`, `no_route`). Between two matched fixes the
marker animates along the road; it is never animated in a straight line across the map. A bus with
no report for 2 minutes is shown as stale and the camera stops following it.
